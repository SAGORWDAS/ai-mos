Part 2

Domain model

Twenty-three modules is a navigation design. Seven services is an engineering design. Conflating the two is how a one-person build turns into twenty-three partially finished applications.

2.1 Why seven services, not twenty-three modules

Each module in the navigation belongs to exactly one service. A service is a deployable unit with its own tables and its own API surface. Most modules are screens over shared tables, not separate backends — the CRM, the pipeline view and the lead table are three presentations of the same rows.

The three rules that keep this honest

  1. One writer per table. A service owns its tables; other services read through its API or through a published view. No cross-service writes.
  2. Events, not calls, for side effects. "Lead qualified" is an event. The outreach service reacts to it. The lead service does not know outreach exists.
  3. Shared platform, not shared database access. Tenancy, authz, audit and cost are platform primitives injected everywhere, and they are the only truly shared code.

2.4 Domain invariants

Six rules hold across the whole system. They are enforced in the database where possible and in the gateway where not. Each maps to a test in Part 14.

#InvariantEnforcement
I-1No row in any tenant table exists without a valid organization_id.NOT NULL + FK + RLS policy. Composite unique keys include the tenant id.
I-2No external action occurs without an approvals row in state approved, unless the action class is pre-authorised at the agent's autonomy level.Gateway check before every tool execution; the approval row is consumed once (unique constraint).
I-3The same logical action never executes twice.Idempotency key (org, action_class, subject_id, attempt_window) with a unique index.
I-4Money state is written only from a verified provider webhook, never from an agent or an email.payments and subscriptions have no write path outside the webhook handler; enforced by a DB role without UPDATE grant for the app role.
I-5A suppressed address is never contacted, on any channel, by any agent, in any campaign.suppressions checked inside the send tool, not by the calling agent.
I-6Every model call produces exactly one model_usage row, including failures.Written in the gateway's finally path; a missing row for a request id is an alert.

2.5.4 Campaign (ENT-campaigns)

draft → planned → pending_approval → approved → active → (paused ⇄ active) → completed, with cancelled and rejected reachable from any pre-active state. Only active may emit sends, and only approved may transition to active.

2.5.5 Approval (ENT-approvals)

pending → approved | rejected | expired; from approved, one-way to executed or revoked (before execution only). An approval binds to a payload hash: if the payload changes, the approval is void and a new one is required. This is what prevents "approved 200 emails" from becoming "approved 2,000 emails".

2.5.6 Conversation and meeting

Conversation: new → triaged → drafting → (auto_replied | awaiting_human) → awaiting_prospect → (meeting_offered | closed_won | closed_lost | opted_out). Any inbound message reopens a closed conversation to triaged. Meeting: proposed → confirmed → booked → (completed | no_show), plus cancelled from any state; availability MUST be re-checked between confirmed and booked.

2.6 Tenancy

Multi-tenancy is not a later feature. Agencies — the second primary segment — run one workspace per client from day one, and a cross-tenant leak is the failure that ends the company.

  request
    |
    v
  [ auth middleware ]  -> resolves user_id, then membership -> organization_id
    |
    v
  [ SET LOCAL app.current_org = '<uuid>' ]   (per transaction, never per connection)
    |
    v
  [ PostgreSQL RLS policy ]
        USING (organization_id = current_setting('app.current_org')::uuid)
    |
    v
  rows of exactly one tenant
  • MUST: RLS enabled on every tenant table, with FORCE ROW LEVEL SECURITY so the table owner is not exempt.
  • MUST: the tenant id comes from the session, never from the request body or query string. A client-supplied organization_id is treated as a hint to validate, never as authority.
  • MUST: background workers set the same session variable before touching tenant data; a worker with no tenant context fails loudly rather than scanning everything.
  • SHOULD: the service role used by migrations is separate from the application role, and the application role has no BYPASSRLS.
Why this is in Part 2 and not Part 10

Tenancy is a data-model property, not a security feature bolted on afterwards. Retrofitting RLS to twenty-eight tables after PH-3 means auditing every query written in the meantime. It costs two days in PH-1 and two weeks later.
