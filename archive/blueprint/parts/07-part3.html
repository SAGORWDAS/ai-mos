Part 3

System architecture

The architecture has one job: make it impossible for an AI model to cause an irreversible external effect that nobody authorised, while still letting it do most of the work.

The brief proposes "LangGraph, introduced gradually". This blueprint defers it entirely until PH-2 exit, and only adopts it if the task graph proves insufficient for cyclic, stateful agent collaboration. The cost of the wrong abstraction in a one-person build is paid in every subsequent debugging session; the cost of adding it later is one refactor with a known boundary.

3.2 The synchronous boundary

One rule prevents most production incidents in this class of product:

MUST

No HTTP request may wait on a model completion, an email send, or any third-party API that is not needed to render the response. Such work is enqueued and its progress is polled or pushed.

OperationBoundaryJustification
Load dashboard metricssyncReads pre-aggregated snapshots.
Save Brand Brain fieldsyncWrite + embedding job enqueued.
Submit a commandsync → jobReturns a plan id immediately; planning runs as a task.
Approve a campaignsync → jobState change is synchronous; dispatch of sends is queued with rate limiting.
Classify an inbound emailjobModel call, retried, never blocks the webhook response.
Book a meetingjobRequires fresh availability; a race with another booking is expected.
Generate a 2,000-word articlejobMinutes, not milliseconds. Streams progress to the UI.

Steps 3–10 are each observable rows. At any moment an operator can answer "what is happening, on whose behalf, at what cost" with one SQL query. That property is worth more than any orchestration framework.

3.4 The tool gateway

Agents never hold credentials, never build HTTP requests and never call a provider directly. They emit a tool request; the gateway decides whether the world changes.

Every step writes an audit_logs entry with the decision and its reason. A rejected action is as important to record as a successful one — it is how you discover that an agent has been trying to do something it should not.

3.5 Worked trace — one email under WKF-B

#ActorAction and record written
1WorkerClaims tasks row for draft_outreach; sets running, attempt 1.
2AI gatewayBuilds context: ICP passage, brand voice passage, lead record, last 0 messages. Tier 1 model. Writes model_usage.
3AgentReturns structured draft: subject, body, personalisation evidence, claims used.
4ValidatorJSON schema + claim check against Brand Brain; unsupported claim → reject, retry once with a stronger tier.
5TaskWrites outreach_drafts, task succeeded.
6WorkerNext task request_send_approval → create_approval with payload hash; task awaiting_approval.
7HumanEdits two words, approves. Edit changes the payload hash — the approval records the edited payload.
8Workersend_email: schema → permission → policy (suppression, consent, cap 40/day) → budget → approval id → idempotency claim.
9GatewayProvider accepts; writes message.sent with provider id; task succeeded; emits event.
10InsightsUpdates campaign counters, cost per send, and the lead's timeline.

Note what is absent: no step asks a model whether the email was sent. Delivery is a provider fact, stored once, and reported from the ledger.

3.7 Observability

  • Logs: structured JSON with org, user, task, agent, tool, trace_id. Human-readable only in development.
  • Traces: one trace per command, one span per task, one child span per model and tool call. This is what makes "why did the agent do that" answerable.
  • Errors: exception capture with the task id attached, so a stack trace lands next to the prompt that produced it.
  • Business alarms: not just CPU. Alert on duplicate provider ids, cross-tenant query attempts, approval bypass attempts, bounce rate > 2%, and cost per task above its type's p95.
  • Weekly truth check: count of messages actually delivered vs count of tasks marked succeeded for send work. A drift between these two is the earliest symptom of a lying system.
