Part 14

Acceptance criteria

A green test suite proves the code does what its author expected. These criteria prove the system does what the business needs — which is a different claim, and the only one that matters.

14.1 The end-to-end scenario

Performed once, end to end, with real systems and a real prospect. It is the acceptance test for the whole product and the script for the first commercial demonstration.

StepActionPass condition
1Complete the Brand Brain profile for a real SaaS product.Positioning, ICP, pricing, approved and prohibited claims are stored and retrievable.
2Enter the objective as one sentence in the Command Center.Parsed objective is displayed and correctable; missing fields are requested, not guessed.
3Review the generated plan before execution.Tasks, agents, dependencies, cost estimate and required approvals are visible.
4Approve the plan.Tasks are created and scheduled; nothing external has happened yet.
5Run lead discovery for a defined segment.Leads appear with source and confidence; duplicates are zero; cost per record is recorded.
6Inspect qualification output.Every qualified lead has a score, a model version and a stated reason.
7Review drafted outreach for ten leads.Each draft cites the brand evidence it used; no unsupported claim; word limit respected.
8Approve the batch, editing one draft.The edited draft requires re-approval; the other nine dispatch.
9Verify delivery.Provider ids stored for each message; delivery counters match the provider's dashboard exactly.
10Receive a reply; let the system classify and draft.Classification confidence and label shown; the draft contains no pricing claim not present in Brand Brain.
11Answer the reply.Sent only after approval (or under an enabled L4 class) and recorded in the thread.
12Process an opt-out.Suppression written immediately; any queued message to that address refused by the gateway with a recorded reason.
13Offer three meeting times; prospect confirms one.Availability re-checked, event created in both calendars, no double booking.
14Send a checkout link; prospect pays.Payment recorded only from a verified webhook; customer and subscription created; onboarding begins.
15Open the dashboard.Leads, replies, meetings, revenue and fully-loaded cost per customer are displayed, each traceable to source rows.
The honest reading of this table

Fifteen steps, of which only step 15 is a dashboard. If the product were built in the order its navigation suggests, this test would be unperformable until the very end — which is exactly why Part 11 builds it in the opposite order.

14.2 Invariant and system tests

Fourteen named tests. Each must exist as an automated test with the given name, and each must fail loudly if the invariant is broken.

IDTestPass condition
AC-01Tenant scoping on createA record created without a session tenant is rejected at the database, not the API.
AC-02Tenant isolation, every tableOrg A's session returns zero rows for Org B on every tenant table, including aggregates and cached reads.
AC-03Suppression blocks sendA suppressed address inside an otherwise approved batch is refused per message, with an audit reason.
AC-04Duplicate execution preventedTwo workers race for one task; exactly one executes and the other records no effect.
AC-05Approval integrityPayload change voids approval; reuse of a consumed approval is refused; expiry is enforced.
AC-06Lead deduplicationRe-running discovery on the same source creates no new rows and does not re-charge data costs silently.
AC-07Budget enforcementExceeding a task budget blocks before dispatch; no partial external effect exists afterwards.
AC-08Ledger completenessEvery model call, including timeouts and refusals, has exactly one usage row; count mismatch raised as an alert.
AC-09Meeting raceTwo prospects confirm the same slot concurrently; one books, the other receives alternatives.
AC-10Webhook authenticityUnsigned, replayed and unknown events produce no state change; each is logged.
AC-11Agent permission ceilingAn action above the configured ceiling is refused at the gateway and escalated, never retried with a different tool.
AC-12Emergency stopStop engaged mid-workflow halts further effects within one task boundary; reads still succeed.
AC-13Restore drillA full restore into a clean environment reproduces row counts and a verified audit chain.
AC-14Claim groundingA generated message containing a fact with no brand citation is rejected by validation in 100% of seeded cases.

14.3 Failure drills

These are performed manually before each phase exit, because most of them cannot be simulated faithfully in unit tests.

DrillExpected behaviour
Revoke the mailbox OAuth grantIntegration shows disconnected; sending fails closed; a re-consent prompt appears; no messages are silently lost.
Exhaust the data provider quota mid-runRun reports partial results with a reason; no partial charge is recorded as complete.
Kill a worker mid-sendTask returns to ready; on retry the idempotency claim prevents a second send; provider shows one message.
Force a model timeout repeatedlyRetries back off, then dead-letter; the task reports failure rather than producing a fabricated success.
Corrupt an approval payloadSend refused; audit records the hash mismatch.
Set a budget to zeroAll model work blocks immediately; reads and UI remain functional.
Deliver a webhook twiceSecond delivery is a no-op; subscription state unchanged.

14.4 Definition of done

Applied to every task in Part 11, without exception. If a task cannot meet all ten, it is not done — it is in progress.

1  Implementation matches the spec row, entity or endpoint it references.
2  Boundary validation exists (user input, provider responses); internal calls are trusted.
3  Happy path covered by a test named after its AC or task id.
4  Named failure path covered by a test; the failure is classified, not swallowed.
5  Tenant scoping verified on every new query or job.
6  Every new external effect routed through the tool gateway with an idempotency key.
7  Cost of the new work is attributable: org, task, agent, and campaign where applicable.
8  Audit entry written for privileged or refused actions.
9  Logs carry org, task, agent and trace id.
10 Demonstration performed once by a human and recorded (screenshot, log excerpt or video).
The single test that matters

When the team disagrees about whether something is finished, ask one question: can you show me the evidence that this happened in the real world? If the answer is a test name, it is correct. If the answer is a screen, it is not.
