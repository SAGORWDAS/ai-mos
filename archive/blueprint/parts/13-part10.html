Security, permissions
and compliance

This system holds other people's inboxes, contact databases and payment relationships. The security model is therefore not a phase; it is a property of every phase.

10.1 Threat model

Eight ways this system causes real harm, with the control that prevents each.

ThreatMechanismControl
Cross-tenant leakA missing filter, a cache keyed without tenant, an aggregate query in a report.RLS with forced policies (2.6); tenant-scoped cache keys; an automated test per table (AC-02).
Agent overreachA model chooses a tool or payload beyond its mandate.Tool allowlist per manifest, autonomy ceiling enforced at the gateway, payload schema validation.
Approval bypassCode path that executes before the approval check, or reuses an old approval.Single-use approvals bound to a payload hash; the check lives inside the tool handler, not the caller.
Prompt injectionContent from a web page, an email reply or a document instructs the model to exfiltrate data or act.Retrieved content is delimited and labelled untrusted; agents cannot read credentials; all actions still pass the gateway; tool arguments are validated against schema, not against model intent.
Reputation damageToo many sends, bad list, no warm-up, ignored complaints.Caps, suppression, complaint thresholds, automatic pause, mandatory approval for any new segment.
Credential lossToken in a log, a prompt, a repo or an n8n workflow.Tokens encrypted at rest, never logged, never placed in prompts; adapters hold them; n8n holds none.
Duplicate billing or duplicate sendsRetry after a timeout that actually succeeded.Idempotency keys at both task and provider level; stored provider ids; replay-safe webhooks.
Silent data lossDestructive migration, cascade delete, purge without export.Reversible migrations, soft delete where recovery matters, documented restore, tested backup.
On prompt injection, specifically

The defence is not a better prompt. It is that the model's output is never trusted as an authorisation. A model that has been persuaded to "send this to everyone" still has to satisfy the tool schema, the permission check, the suppression list, the send cap and — where required — a human. Prompt injection can waste tokens; it cannot send mail.

10.3 Consent, suppression and lawful basis

Cold outreach sits on different legal ground in different jurisdictions. The system must model that rather than assume.

RequirementWhat the build must do
Lawful basis per contactRecord lawful_basis and basis_evidence (source, date, jurisdiction) on every contact used for outreach. No basis, no send.
Jurisdiction rulesA per-tenant config declares the regimes it operates under. Opt-out handling is mandatory everywhere; prior consent is mandatory in opt-in regimes, and the UI must block a campaign whose segment violates the setting.
SuppressionOrganisation-wide, channel-specific, checked inside the send tool, surviving data purges. Hard bounce and complaint write suppressions automatically.
UnsubscribeOne-click in bulk mail plus a monitored reply path; honoured within 24 hours, immediately at the tool level.
IdentificationSender identity and a physical address in every commercial message, configured per tenant and validated before enable.
Data subject requestsExport and delete per contact across messages, leads and enrichment; suppression retained.
AI disclosureTenant-level setting for whether automated replies disclose automation; default on for regulated segments.

10.4 Secrets and access

  • Provider tokens encrypted at rest with a key held outside the database; never logged, never included in a prompt, never returned by an API.
  • The webhook handler and the application run with different database roles; the application role cannot update payment tables.
  • Human access to production follows least privilege with named accounts; no shared admin credential.
  • Key rotation is a documented procedure with a test, not an aspiration. Rotating the AI provider key must not require a deploy.
  • Every privileged human action — impersonation, data export, stop, deletion — writes an audit entry with a reason.

10.5 Audit and review

Three layers, each answering a different question.

LayerAnswersContents
Audit log"Who did what, and was it allowed?"Append-only rows for every privileged action, including rejected and escalated ones.
Execution history"Why did the system do that?"Task-level trace: agent, model, prompt hash, tool calls, validations, cost.
Weekly digest"Is the system behaving?"Autonomous actions taken, approvals outstanding, rejections by reason, spend by agent, deliverability metrics, failed tasks.

The digest is the cheapest control in this document. It is also the one most often skipped. An owner who reads forty lines a week will catch a misbehaving agent long before any test suite does.
