Part 11

Phased delivery plan

Seven phases. Each has an entry gate, a task ledger, and an exit gate that is a business outcome rather than a feature list. The order is the plan; the calendar is not.

11.1 Why gates instead of weeks

The source brief proposed a twelve-week schedule. Schedules assume a known duration for work whose main risks — provider approval, model quality, deliverability, payment eligibility — are outside the builder's control. Gates replace dates with dependencies that are true regardless of how fast the work goes.

 PH-0  Decisions        no product code exists yet
   |
 PH-1  Foundation       one agent task runs, costed, audited
   |
 PH-2  Marketing        a command becomes an approved, costed plan
   |
 PH-3  Acquisition      ten real emails are sent and answered        <-- the proof
   |
 PH-4  Revenue          a demo is booked, paid for, and onboarded
   |
 PH-5  Learning         cost per customer is computed from real data
   |
 PH-6  Scale            a second tenant is isolated and a restore is proven

Two rules govern the sequence. Nothing in a later phase is started to unblock an earlier one — if PH-3 is hard, the answer is a better PH-3, not a head start on PH-5. And a phase is not exited because the code exists; it is exited when the demonstration in its exit gate has been performed once, successfully, with evidence.

11.9 Sequencing rules

  • Never build a screen before its data exists. Eleven of the twenty-three modules are reads; they cost a day each once the tables are proven and weeks if built first.
  • Never build an agent before its tool. An agent without a working, permissioned tool produces plausible text that changes nothing — the most expensive kind of progress.
  • Never ship an integration before its failure path. Token expiry, quota exhaustion and provider outages are the normal case, not the exception.
  • Never enable L4 for a new action class without a week of L3 evidence. Autonomy is earned with the digest, not granted by configuration.
  • Never let a phase exit without its demonstration having been performed once. A green test suite is evidence of correctness, not of usefulness.
