Part 8

API surface

One REST surface, generated from typed models, used by both the dashboard and any future client. Conventions are fixed once so that every endpoint behaves identically.

8.1 Conventions

ConcernRule
Base path/v1. Breaking changes require /v2; additive changes do not.
AuthSession cookie for the dashboard (HttpOnly, SameSite=Lax, CSRF token on state-changing routes); bearer token for machine access, scoped per tenant.
Tenant contextResolved from the session or token. A client-supplied organization_id is validated against membership, never trusted.

PaginationCursor-based: ?limit=50&cursor=…, response contains next_cursor. Never offset pagination on mutable tables.

8.4 Webhooks

DirectionProviderHandling rule
InboundPayment providerVerify signature against the raw body. Store provider_event_id with a unique constraint. Respond 2xx before doing work; process as a job. Replays are no-ops.
InboundGmail / Graph pushValidate channel token, resolve the mailbox to an integration, enqueue a sync job. Never parse message content in the webhook handler.
InboundCalendar changeInvalidate availability cache for that user; do not reschedule anything automatically.
OutboundCustomer systemsSigned with an HMAC over the body and a timestamp; retries with backoff for 24h; failures visible in the UI.
MUST

Payment state changes only inside the webhook handler, only after signature verification, and only for events this system recognises. A missing or unknown event type is logged and ignored — never inferred from the accompanying email, the checkout redirect, or the model's opinion.

8.5 Versioning

Additive fields are free. Removing or renaming a field, changing a default that alters behaviour, or changing an error code requires a new major path and a 90-day overlap. The dashboard and the public API share the same version, so a v2 is a product decision, not a developer convenience.

Part 9

Integrations

Every external system is a liability with a quota. Integrate through official APIs, assume every provider will fail, and design so that its failure is a visible state rather than a silent one.

9.1 Sourcing policy

MUST NOT

The product MUST NOT be built around scraping platforms that prohibit it, bypassing access controls or rate limits, or reselling data without a licence. This is not only a legal position — it is a commercial one: a growth engine that is banned from the channels it depends on has no product.

Prospect data therefore comes from three sources only: licensed data providers, first-party interactions (form fills, replies, website activity the tenant owns), and public information fetched politely with attribution and cached. Every lead record carries source and source_confidence, and the UI says so plainly rather than implying verified contactability.

The adapter rule

Each integration is one adapter module exposing the same internal interface: connect, refresh, health, and a small set of typed operations. Provider-specific identifiers, error shapes and rate-limit semantics live inside the adapter and never leak into services or prompts. Swapping Gmail for an ESP is then a configuration change on one mailbox, not a rewrite of the outreach workflow.

9.3 Deliverability — the part most builds get wrong

The brief proposes Gmail for both reading and sending. That is correct for one case and dangerous for the other.

Use caseRecommended channelWhy
Conversational replies to a thread the prospect startedGmail / Graph (the mailbox itself)Continuity matters more than throughput; it looks and behaves like the founder writing.
Cold or bulk outreach at volumeDedicated ESP on a dedicated subdomainPer-mailbox quotas, reputation isolation, bounce and complaint APIs, and protection of the primary business domain if something goes wrong.
Transactional mail (receipts, onboarding)ESP transactional streamSeparate reputation from marketing; must never be affected by a campaign.

Non-negotiable mechanics for any sending path:

  • SPF, DKIM and DMARC configured and verified before the first send; a domain that fails verification cannot be enabled in the UI.
  • Warm-up schedule for a new domain or mailbox, enforced in configuration rather than in an operator's memory.
  • Per-mailbox daily caps, per-domain caps, and a global campaign cap — all enforced atomically.
  • Bounce handling that distinguishes hard from soft; a hard bounce suppresses immediately and is never retried.
  • Complaint thresholds wired to an automatic pause. Exceeding the provider's rate is not a warning; it is a stop.
  • One-click unsubscribe links in every bulk message, and a plain reply-to-unsubscribe path that a human monitors.

9.4 Regional constraints

The brief notes Bangladesh-based operations. This is a decision gate in PH-0, not a detail discovered in PH-4, because it can invalidate the payment path entirely.

QuestionWhy it blocks the buildWhen it must be answered
Can the business open a merchant account with the chosen provider?No merchant account, no subscriptions, no revenue — the product's core loop is impossible.PH-0, before any code
Which settlement currencies and payout countries are supported?Determines pricing currency and possibly a required intermediary entity.PH-0
Are there local alternatives with webhooks and subscription objects?A provider without webhooks breaks invariant I-4 and the entire money model.PH-0
Can a sending domain be verified and warmed from this jurisdiction?Determines whether PH-3 is achievable at all within the phase.PH-0

The architectural answer is a payment adapter with a single internal contract, so provider choice can change without touching subscriptions, onboarding or reporting. The commercial answer must come from a human in PH-0.
