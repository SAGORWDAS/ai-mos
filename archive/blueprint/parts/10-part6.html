Part 6

Module build sheets

One sheet per module, written so a developer can start without asking a question. The ten P0 modules are specified in full; the remainder are specified to the level needed to size them, and will be expanded at their phase entry.

Every sheet follows the same shape: what it is for, what a user does in it, which routes serve it, which entities it owns, which agents depend on it, and the condition under which it is finished. Nothing here redefines a table or an endpoint — those live in Part 7 and Part 8.

MOD-02

Command Center

SVC-growth-strategy · PH-2 · P0

Purpose. The only entry point for an objective. Converts one natural-language instruction into a validated objective, a plan, and a task graph. It is not a chat window: it accepts a goal, shows what it understood, and hands over to the planner.

User storiesAs an owner, I state a growth goal and see exactly what the system understood before anything runs. As an owner, I can edit the parsed objective instead of re-typing the command.
Routes/command · /command/[id]/plan
EndpointsPOST /v1/commands · GET /v1/commands/{id} · POST /v1/commands/{id}/confirm
Ownscommands, objectives
Depends onAGT-01 (parsing and planning), MOD-18 (Brand Brain) for grounding, budget check before dispatch.
AcceptanceAn ambiguous objective produces a clarification request listing the exact missing fields, never a guess. Confirming an objective creates a plan and task rows in one transaction.
MOD-03

AI Manager — orchestration

SVC-growth-strategy · PH-2 · P0

Purpose. Turns a confirmed objective into a dependency graph of tasks, assigns each to a role, estimates cost, and reports progress. The plan is a database object, editable by a human before execution.

User storiesAs an owner, I see the plan as a list of tasks with owners, dependencies, estimated cost and required approvals before anything executes. As an operator, I can pause or cancel any task and see why it failed.
Routes/manager · /manager/[planId] · /manager/tasks/[id]
EndpointsPOST /v1/plans · GET /v1/plans/{id} · PATCH /v1/tasks/{id} · POST /v1/tasks/{id}/cancel
Ownsplans, tasks, task_dependencies
Depends onAGT-01; scheduler; every role's manifest for cost estimation.
AcceptanceA plan cannot contain a cycle (rejected at write time). No task starts before all dependencies succeed. Cancelling a parent cancels descendants with a recorded reason.
MOD-04

AI Agents — registry and permissions

SVC-growth-strategy · PH-1 · P0

Purpose. The console for the twenty roles: toggle availability per organisation, set autonomy ceilings, inspect tools granted, view execution history and per-agent cost.

User storiesAs an admin, I can see what every agent is allowed to do in one screen. As an owner, I can lower an agent's autonomy without editing a file or deploying.
Routes/agents · /agents/[id] · /agents/[id]/runs
EndpointsGET /v1/agents · PATCH /v1/agents/{id} · GET /v1/agents/{id}/runs
Ownsagents, agent_tools
Depends onPlatform authz; tool registry; model registry.
AcceptanceLowering an autonomy ceiling takes effect on the next task, with no caching of the old value. Raising a ceiling to L4 for a money-related action class is rejected by the API.
MOD-18

Brand Brain

SVC-growth-strategy · PH-1 · P0

Purpose. The source of truth every agent must consult. Structured fields plus document uploads, chunked and embedded, with approved and prohibited claims treated as hard constraints rather than guidance.

User storiesAs an owner, I complete a business profile once and every agent uses it. As an owner, I mark a claim as prohibited and see it blocked in generated copy.
Routes/brand · /brand/documents · /brand/claims
EndpointsGET|PUT /v1/brands/{id} · POST /v1/brands/{id}/documents · GET /v1/brands/{id}/search
Ownsbrands, brand_documents, brand_chunks
Depends onpgvector; embedding job; storage.
AcceptanceAn agent cannot produce a claim without a brand_chunk_id citation. Deleting a document removes its chunks in the same transaction. Search returns passages, never whole documents.
MOD-20

Approval Center

SVC-growth-strategy · PH-2 · P0

Purpose. The single queue where a human authorises external effects. One request, one payload hash, one decision, one expiry.

User storiesAs an owner, I see exactly what will be sent, to whom, and at what cost, and I approve or edit it. As a reviewer, I can approve a batch of similar items with one action, but never a batch that exceeds the configured cap.
Routes/approvals · /approvals/[id]
EndpointsGET /v1/approvals · POST /v1/approvals/{id}/approve · POST /v1/approvals/{id}/reject
Ownsapprovals, approval_rules
Depends onEvery gated tool; notification channel.
AcceptanceApproving a payload that has changed since review is impossible. An approval is single-use. An expired approval cannot be resurrected. Rejection is recorded with a reason and blocks the task permanently.
MOD-06

Lead Generation

SVC-acquisition · PH-3 · P0

Purpose. Discover candidate companies and people from permitted sources, deduplicate against the tenant's existing data, enrich, and hand qualified records to the CRM.

User storiesAs an owner, I describe my ICP and receive a reviewable list with sources and confidence, not a claimed-verified list. As an owner, I can reject a segment and see why records failed.
Routes/leads · /leads/discover · /leads/[id]
EndpointsPOST /v1/leads/discover · GET /v1/leads · GET /v1/leads/{id} · POST /v1/leads/{id}/qualify
Ownsprospects, leads, lead_sources
Depends onAGT-04, AGT-05; permitted data provider (INT-05); dedupe service.
AcceptanceZero duplicates within a tenant on (domain, contact_hash). Every contact carries source and confidence; no record is presented as verified without a verification event. A discovery run that returns fewer records than requested reports why.
MOD-07

CRM

SVC-acquisition · PH-3 · P0

Purpose. Companies, contacts, pipeline stages and a per-record timeline. Deliberately small: it holds what the growth engine needs, and exports what an external CRM wants.

User storiesAs a sales user, I see every interaction with a contact in one timeline. As an owner, I move a lead between stages and the change is attributed to me, not to an agent.
Routes/crm · /crm/companies/[id] · /crm/contacts/[id] · /crm/pipeline
EndpointsGET|POST /v1/companies · GET|PATCH /v1/contacts/{id} · GET /v1/pipeline · POST /v1/leads/{id}/stage
Ownscompanies, contacts, pipeline_stages, activities
Depends onLead service; message service; audit.
AcceptanceEvery stage change writes an activity row with actor type (human or agent) and id. Field-level permissions prevent an agent from editing owner-assigned fields.
MOD-08

Outreach Studio

SVC-acquisition · PH-3 · P0

Purpose. Drafts, review and dispatch of personalised first touches and follow-up sequences, with per-sender caps and a suppression gate that the drafting agent cannot bypass.

User storiesAs an owner, I review a batch of drafts, edit any of them, and approve the batch. As an owner, I set a daily cap and the system respects it even under load.
Routes/outreach · /outreach/[campaignId] · /outreach/sequences/[id]
EndpointsPOST /v1/outreach/drafts · GET /v1/outreach/drafts · POST /v1/outreach/dispatch · GET /v1/outreach/sequences/{id}
Ownsoutreach_drafts, sequences, sequence_steps
Depends onAGT-06, AGT-07, AGT-09; TLS-14; suppression list; approvals.
AcceptanceEditing a draft invalidates its approval. A suppressed address cannot be dispatched even if present in an approved batch — the send tool refuses per message and records why. Caps are enforced atomically across workers.
MOD-09

AI Sales Inbox

SVC-acquisition · PH-3 · P0

Purpose. Retrieves replies, classifies intent, drafts responses grounded in Brand Brain, and routes anything uncertain to a human. This is where the product either earns trust or loses it.

User storiesAs an owner, I see every reply with a suggested response and a one-click approve. As an owner, I can see exactly which brand facts the draft used.
Routes/inbox · /inbox/[conversationId]
EndpointsGET /v1/conversations · GET /v1/conversations/{id} · POST /v1/conversations/{id}/reply · POST /v1/conversations/{id}/classify
Ownsconversations, messages
Depends onAGT-08; INT-02 (Gmail) or INT-07 (Graph); classification golden set.
AcceptanceA reply classified below the confidence threshold is never auto-sent at any autonomy level. An opt-out keyword immediately writes a suppression and stops the sequence, before any other processing. Threading matches the provider's thread id, not the subject line.
MOD-13

Campaign Manager

SVC-content · PH-3 · P0

Purpose. Binds a segment, a message, a channel and a budget into one unit of work whose results are measurable. A campaign is the join key that makes cost per lead computable.

User storiesAs an owner, I see one campaign's full economics — spend, leads, replies, meetings, revenue. As an owner, I pause a campaign and no further messages leave.
Routes/campaigns · /campaigns/[id] · /campaigns/new
EndpointsPOST /v1/campaigns · GET /v1/campaigns/{id} · POST /v1/campaigns/{id}/activate · POST /v1/campaigns/{id}/pause
Ownscampaigns, campaign_assets, campaign_metrics
Depends onAGT-12; approval; insights.
AcceptanceActivation requires a prior approval. Pausing takes effect before the next send, not after the queue drains. Every send carries campaign_id, so no cost is unattributable.
MOD-17

Analytics and Overview

SVC-insights · PH-2 · P0

Purpose. Immutable activity events rolled up into metric snapshots, plus the overview screens. Numbers come from SQL; the model only narrates them.

User storiesAs an owner, I can trace any number on the dashboard back to the rows that produced it. As an owner, I see cost per qualified lead and per won customer, not only token spend.
Routes/dashboard · /analytics · /analytics/campaigns/[id]
EndpointsGET /v1/metrics/overview · GET /v1/metrics/campaigns/{id} · GET /v1/metrics/costs
Ownsanalytics_events, metric_snapshots
Depends onevery emitting service; the rollup job.
AcceptanceAn agent cannot write a metric. Every dashboard figure has a documented query. Snapshots are recomputable from events and a rebuild produces identical totals.

A note on module count

Eleven of the twenty-three modules are reads over tables another module owns. Building them as separate services would triple the surface area for no benefit. The navigation stays at 23 because that is how users think; the implementation collapses to seven because that is how systems stay operable.
