Part 4

Agent runtime

There is one agent engine. A "CMO Agent" and a "Lead Qualification Agent" differ by configuration — instructions, tools, model tier, permissions, output schema — not by code path.

4.1 One engine, many roles

The temptation is to build twenty small applications. The consequence is twenty prompt stacks, twenty logging formats, twenty permission models and no way to answer "what did the system do yesterday". Instead:

        agent manifest (YAML / row)          task instance
  +-----------------------------------+     +------------------+
  | id, role, persona instructions    |     | input payload    |
  | model tier + fallback tier        |     | org + brand      |
  | allowed tools + max autonomy      |---->| context budget   |
  | input/output JSON schema refs     |     | deadline         |
  | token + cost + time limits        |     +--------+---------+
  | memory scopes, escalation policy  |              |
  +-----------------------------------+              v

                                            | 1 assemble context |
                                            | 2 call model       |
                                            | 3 parse + validate |
                                            | 4 tool calls? loop |
                                            | 5 evaluate output  |
                                            | 6 persist + bill   |

4.2 The manifest

Every agent is data. The manifest below is the complete shape; the Appendix C version is the template to copy.

id: AGT-07
name: Outreach Agent
version: 3
status: active

persona: |
  You are an outreach specialist. You write one short, specific email to one person.
  You never invent a fact. If you cannot ground a personalisation claim in the
  provided evidence, you write a generic but honest email and say so in the evidence field.

model:
  tier: 1
  fallback_tier: 2
  temperature: 0.4
  max_input_tokens: 6000
  max_output_tokens: 1200

tools:
  allowed: [TLS-02, TLS-05, TLS-07, TLS-13]
  forbidden: [TLS-14]          # drafting never sends, even with permission

permissions:
  autonomy_ceiling: L3         # may request a send; requires approval to execute
  max_actions_per_task: 1
  budgets: { task_usd: 0.02, day_usd: 5.00 }

io:
  input_schema: schemas/outreach_input.json
  output_schema: schemas/outreach_draft.json

memory:
  brand_brain: retrieval     # pgvector, top-k with score threshold
  conversation_history: 0    # first touch: no history by design
  learned_lessons: true

guards:
  claim_check: required      # every claim must cite a brand_chunk_id
  banned_phrases: brand/claims.yaml#prohibited
  max_words: 140

escalation:
  on_validation_failure: retry_with_tier_2_once
  on_low_confidence: human
  on_policy_reject: human_notify

eval:
  dataset: evals/outreach_golden.jsonl
  min_score: 0.78
  metrics: [groundedness, specificity, subject_quality, spam_risk]

Four properties of this manifest matter more than the rest:

  • Tool allowlists are exclusive. Listing a tool grants nothing until the tool itself validates the caller's autonomy level and the payload.
  • Budgets are per-task and per-day. A runaway loop hits a wall in cents, not in dollars.
  • Guards are deterministic. Claim checking, banned phrases and word limits are code, not instructions in a prompt. A model can ignore an instruction; it cannot ignore a validator.
  • Eval is part of the manifest. Changing a prompt without running the golden set is a change without a test.

4.3 Context assembly

Most of the money in this product is spent in this section. The rule is that context is selected, not concatenated.

Context blockBudgetRule
System instructions~400 tokVersion-hashed and cacheable. Never varies per request; any variation is a new agent version.
Brand slice~800 tokRetrieved by the current task's intent, not "the whole brand". Threshold on similarity score; drop low-relevance chunks rather than padding.
Task input~600 tokThe structured row plus the minimum fields the task needs. Never the entire entity.
Conversation0–1,200 tokSummarised beyond the last 4 turns. First-touch outreach carries zero history deliberately.
Retrieved facts~600 tokResearch results and enrichment, each with source and retrieval date so the model can attribute.
Learned lessons~300 tokTop-3 relevant learning_records by embedding similarity, only where the manifest enables it.
Output schema~200 tokJSON schema, enforced by the provider where supported.
The cheapest optimisation in the product

Storing business knowledge in Postgres and retrieving it beats re-sending it in prompts by an order of magnitude — and it is the difference between an agent that says "we integrate with HubSpot" because it read it, and one that says it because it seemed plausible. Retrieval is a correctness feature before it is a cost feature.

4.4 Structured output

No agent returns prose to another agent. Every handoff is a JSON object validated against a schema referenced in the manifest.

  1. Request with the provider's structured-output mode where available; otherwise a schema in the prompt plus a strict parser.
  2. Parse. On parse failure, one repair attempt with the parser error appended.
  3. Semantic validation: required citations present, numbers within plausible ranges, no fields invented outside the schema.
  4. On second failure, retry once at fallback_tier.
  5. On third failure, fail the task and escalate. Never silently accept a partly parsed object.

4.5 Autonomy

LevelPermissionWhat the gateway permitsNever at this level
L1Read and analyseRetrieval, search, classification, scoring, reporting.Any write.

L4 exists so that the system can be genuinely useful without a human present — but it is opt-in per action class, disabled by default, and every L4 action is still written to the audit log and reviewed in the weekly digest.

4.6 Evaluation

Every role has a golden set built from the business's own real examples, not from public benchmarks. A model change, a prompt change or a tier change runs against it before promotion.

Role familyGolden setPass criteria (illustrative)
Qualification300 labelled leads≥ 85% agreement with human labels; false-positive rate on disqualified < 10%.
Outreach100 approved historical emailsGroundedness 1.0 (no unsupported claims), specificity ≥ 0.7, human edit distance within tolerance.
Reply handling200 labelled repliesIntent accuracy ≥ 90%; zero pricing claims where price is unconfigured.
Strategy20 past plansHuman rubric: structure, feasibility, budget realism, no invented capability.
Content50 published piecesBrand voice match, factual accuracy, prohibited-claims count = 0.

Two operational rules follow. First, evaluation runs before a model is promoted, never after (Part 5.7). Second, evaluation results are stored against the agent version so a regression can be traced to the change that caused it.
