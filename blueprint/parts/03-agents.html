Instructions for automated
coding agents

This page is written for an AI coding agent, not for a person. If you are a language model asked to implement AI-MOS, read this page before anything else, then follow the ingest order exactly.

Ingest order

1. spec/ai-mos.spec.yaml        -> canonical registry: modules, agents, tools, phases, tasks
2. Part 11 of this PDF          -> the phase you are authorised to build
3. spec/phase-tasks.yaml        -> the task graph and its dependencies
4. Part 2 + Part 7 of this PDF  -> entities, state machines, table definitions
5. Part 3 + Part 4 of this PDF  -> the invariants your code must never break
6. spec/schemas/*.json          -> exact output shapes for agent-facing APIs

spec/ai-mos.spec.yaml is normative. Where this prose and the spec disagree, the spec wins and the prose is a defect to be reported — never resolved by inference.

Operating rules

  1. Work one task at a time. Tasks are identified as T-n.m. Do not begin T-n.m+1 until T-n.m satisfies its definition of done. Do not batch-implement a phase.
  2. Never invent a schema. Every table, column, endpoint and agent output shape exists in Part 7, Part 8, Appendix A or Appendix B. If a needed shape is missing, stop and report SPEC-GAP: <what is missing> <why it blocks T-n.m>.
  3. Never invent a model identifier. The identifiers in Part 5 are marked status: unverified. Treat them as registry slots, not literals. A model string MUST NOT appear in business logic; it is loaded from configuration.
  4. Never invent a number. Prices, limits and cost estimates marked illustrative are placeholders. They belong in configuration with an explicit verify_at_build note.
  5. Every external action goes through the tool gateway. Code that calls Gmail, a calendar, a payment provider or an ad platform from anywhere other than a registered tool handler is wrong, regardless of whether it works. See Part 3.4.
  6. Tenant isolation is not optional. Every query on tenant data MUST be scoped by organization_id, enforced at the database layer and not only in application code. A test proves this for every table (AC-02).
  7. Write the test with the code. A task is not done when the happy path runs; it is done when its named acceptance test passes and its failure path is exercised.
  8. Emit attributable logs. Every log line carries organization_id, task_id, agent_id and trace_id. A line that cannot be attributed to a tenant and a task is not useful in production.
  9. Stop conditions. Stop and ask a human when: a task needs a credential you do not have; a requirement conflicts with a MUST rule; a migration would destroy data; a decision listed as an open ADR in Part 13.2 is still undecided; or the task touches money, refunds or bulk sending without an approval path already implemented.

Output contract per task

ArtifactRequired content
MigrationReversible and ordered. No destructive change without a task that explicitly authorises it. Naming: YYYYMMDDHHMM_<task-id>_<slug>.
CodeValidate at boundaries only — user input and external APIs. Trust internal calls. No dead code, no compatibility shims.

CommitT-3.4: enforce suppression list before send — one task, one commit, task ID first.
ReportTask ID, files changed, test evidence, any SPEC-GAP or deviation. No narrative summary of what the code obviously does.

What you are not asked to do

You are not asked to design the product, choose the stack, invent agents, select models or set pricing. Those decisions are made here, several of them deliberately and with reasons (Part 13.2). Implementing an unrequested improvement is a defect: it breaks the traceability between specification and running system, which is the entire point of this build.

The failure mode to avoid

This project will not fail because a feature is missing. It will fail by producing impressive-looking output while quietly breaking one invariant: an agent that sends without approval, a query that crosses tenants, a task that runs twice and bills twice, or a campaign reported complete that was never actually sent. Every phase exit gate in Part 11 exists to catch exactly those four failures.
