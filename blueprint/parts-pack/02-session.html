Section 1

How to run a build session

The unit of work is one task. Not one phase, not one feature, not one afternoon of "refactoring". A session that ends with two task IDs in the changelog is a session that produced two untested changes.

The loop

#StepWhat you actually do
1Pick the taskFirst task in the current phase whose dependencies are done. If a dependency is not done, that is the task.
2Load the capsulespec/tasks/T-n.m.yaml. It names the files, the two spec slices and the stop condition. Load nothing else.
3Read the two slicesOnly the sections the capsule names — one table definition, one state machine, one schema. Never the whole Part.
4Write the failing test firstNamed after the acceptance criterion: test_AC-02_tenant_isolation_leads.
5Implement until it passesOnly the files on the card. A new file is a decision — if it is not listed, report a gap instead of inventing it.
6Run the definition of doneAll ten items in §9, not the three you remember.
7Commit and stopT-n.m: <title>. Do not start the next task in the same session.

These are ceilings for input context before the first edit. They are what keep a session cheap and keep the model focused.

Never load the blueprint PDF, the full spec YAML, or a second phase's files. Never batch two tasks into one session — the second test suite always gets written after the second change, which proves neither. If you catch yourself summarising what you just read, you loaded too much: drop to the capsule.

When you are stuck

SituationAction
The capsule is missing somethingStop. Report a SPEC-GAP (§10 template B). Do not infer a shape.
Two rules conflictStop. Quote both. The MUST rule wins; the other is a document defect.
A credential is missingPut the path behind an interface; mark it unverified in the commit body.
The task touches money or bulk sendingStop unless the approval path is implemented and tested. Not a scheduling preference.
You want to fix something nearbyDo not. Propose a card and finish the current task.
